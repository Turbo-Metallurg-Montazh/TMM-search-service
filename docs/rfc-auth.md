# Анализ вариантов авторизации для вызовов Search Service из основного backend

### Цель:
Цель данного RFC - провести сравнительный анализ возможных механизмов авторизации для вызовов Search Service из основного backend, оценить их с точки зрения безопасности, производительности, сложности внедрения и сопровождения, а также выбрать рекомендуемый подход, который станет стандартом для взаимодействия сервисов в рамках платформы.

### Контекст:
В настоящее время основной backend взаимодействует с Search Service напрямую по REST API. Механизм сквозной авторизации для межсервисных запросов отсутствует. Единственный существующий механизм защиты - middleware `origin_guard_mw`, которое проверяет значения заголовков `Host`, `Origin` и `Referer` на соответствие спискам разрешённых источников (`ALLOWED_HOSTS`, `ALLOWED_ORIGINS`).
Такой подход может быть достаточным для ограничения запросов, поступающих из браузера, однако не обеспечивает надёжную защиту при взаимодействии между сервисами. Указанные HTTP-заголовки могут быть сформированы или изменены клиентом, поэтому их проверка не может рассматриваться как механизм аутентификации.
С учётом дальнейшего развития системы, появления новых сервисов и интеграций, целесообразно внедрить полноценный механизм аутентификации и авторизации межсервисных запросов, соответствующий современным требованиям безопасности.

### Требования к будущему решению:
#### Выбранный механизм авторизации должен удовлетворять следующим требованиям:
* Надежная аутентификация.
* Автономная проверка.
* Минимальный оверхед.
* Совместимость с FastAPI.

### Сравнения возможных решений:
| Вариант                         | Безопасность  | Сложность внедрения | Плюсы                                                                                                                           | Минусы                                                                             |
|---------------------------------|---------------| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Authorization: Bearer Token** | Высокая       | Средняя             | Современный подход, поддерживает срок жизни токенов и разграничение доступа                                                     | Требуется механизм выпуска и проверки токенов                                      |
| **X-API-Key**                   | Средняя       | Низкая              | Простая реализация, минимальные изменения                                                                                       | Статический ключ, необходима ротация, ограниченные возможности управления доступом |
| **Basic Authentication**        | Низкая        | Низкая              | Очень простая реализация                                                                                                        | Передача логина и пароля в каждом запросе, устаревший подход                       |
| **JWT от Backend**              | Очень высокая | Средняя             | Высокая безопасность, возможность передавать информацию о сервисе, не требует запроса к серверу авторизации при каждой проверке | Необходимо реализовать выпуск и проверку JWT                                       |

### Предлагаемое решение
В качестве механизма авторизации запросов между основным Backend и Search Service предлагается использовать JWT.
Основной Backend формирует и подписывает JWT, содержащий информацию о вызывающем сервисе. При обращении к Search Service токен передается в заголовке: `Authorization: Bearer <токен>`.
Вместо глобального Middleware на стороне Search Service валидация токенов и разграничение прав будут реализованы с помощью **нативного механизма зависимостей FastAPI (`Depends`)**. На уровне эндпоинтов или роутеров Search Service внедряется зависимость, которая выполняет проверку подписи, срока действия токена, а также проверяет соответствие необходимых прав, после чего принимает решение о предоставлении доступа к запрашиваемому ресурсу.

### Альтернативы
#### Рассмотренные альтернативы (X-API-Key, Basic Authentication и mTLS) имеют следующие ограничения:
* **X-API-Key** - Ключ статический. Если его кто-то перехватит, злоумышленник получит полный доступ. Кроме того, через один ключ сложно гибко настроить разные права доступа.
* **Basic Authentication** - считается устаревшим механизмом для межсервисного взаимодействия и не рекомендуется для новых проектов.
* **mTLS** - Слишком сложен в поддержке. Нужно разворачивать целую систему, чтобы выпускать, безопасно хранить и постоянно обновлять эти сертификаты. Для текущих задач нашего проекта это избыточно.

Таким образом, использование JWT в связке с зависимостями FastAPI обеспечивает оптимальный баланс между безопасностью, простотой интеграции и дальнейшей масштабируемостью решения.

### Почему FastAPI зависимости, а не middleware
Переход от использования глобального Middleware к нативным зависимостям (`Depends`) обусловлен несколькими архитектурными преимуществами:
* **Гибкое управление правами (Scopes) на каждом эндпоинте:** Middleware перехватывает абсолютно все запросы к приложению «ковровым» методом. Реализовать внутри него логику «эндпоинту А нужен доступ на чтение, а эндпоинту Б - на запись» крайне неудобно, так как приходится вручную парсить URL-адреса и заводить громоздкие списки исключений. Зависимости позволяют гибко передавать параметры авторизации прямо в декларацию конкретного роута.
* **Автоматическая документация в Swagger / OpenAPI:** FastAPI нативно не знает, что происходит внутри кастомного Middleware, поэтому в сгенерированном Swagger-документе все эндпоинты будут отображаться как публичные. Использование зависимостей, наследующих `HTTPBearer`, автоматически добавляет схемы безопасности в OpenAPI - у защищенных эндпоинтов появляется значок «замочка», позволяя тестировать запросы прямо из браузера.
* **Выборочное применение без списков исключений:** Для технических публичных эндпоинтов (например, `/health` или `/metrics`) при использовании Middleware приходится писать явные проверки на пропуск. С зависимостями защита применяется точечно: они вешаются только на те роутеры или эндпоинты, которые действительно необходимо закрыть.
* **Строгая типизация и нативный доступ к данным:** Зависимость может сама расшифровать токен и сразу передать готовые данные (например, имя сервиса или список его прав) прямо внутрь функции эндпоинта. С Middleware так сделать не получится — данные пришлось бы «прятать» внутри объекта запроса, из-за чего код становится запутанным, а среда разработки (IDE) перестает давать подсказки.

### Последствия внедрения решения
#### Положительные:
* Исключается несанкционированный доступ к операциям, таким как `/catalogs/upload-many`.
* Появляется возможность настраивать точечные права доступа. Например, одному сервису можно разрешить только проверять, работает ли система, а админ-сервису - массово удалять каталоги.
* Документация Swagger (OpenAPI) обновится сама: в интерактивной документации у каждого защищенного эндпоинта автоматически появится значок «замочка», и можно будет сразу увидеть, какой токен нужен для вызова. 
#### Отрицательные / Риски:
* Токен работает автоматически до тех пор, пока не закончится его срок. Если злоумышленник украдет секретный ключ системы, он сможет беспрепятственно совершать любые действия. Этот доступ закроется только после того, как мы вручную поменяем ключ на сервере.
* Благодаря кэшированию токена на стороне Backend, риск «Проверка подписи JWT создает небольшую вычислительную нагрузку на CPU» минимизируется для отправляющей стороны (Backend делает это раз в 9-10 минут, а не на каждый из 10 000 запросов). Нагрузка останется только на стороне Search Service, который проверяет подпись входящих запросов в вызываемой зависимости.

### Минимизация рисков
* Установить минимальное время жизни токена (~10 минут).
* Убрать ключи из исходного кода и хранить их в защищенном месте, а приложение будет получать их через переменные окружения при запуске.
* Провести нагрузочное тестирование перед внедрением.
* **Асинхронное шифрование:** Перейти на алгоритм RS256/EdDSA, чтобы изолировать приватный ключ на стороне Backend. На стороне Search Service для проверки будет находиться только публичный ключ.

### Принцип работы предлагаемого решения
![Search_service_auth_diagram.png](Search_service_auth_diagram.png)
#### Более подробно:
1. **Получение токена Бэкендом:** Перед отправкой запроса Бэкенд проверяет локальный кэш. Если валидный токен с не истекшим сроком действия уже есть в памяти, используется он. Если токена нет или до его истечения осталось менее 1 минуты, Бэкенд генерирует новый JWT-токен (время жизни - 10 минут), подписывает его приватным ключом и обновляет кэш.
2. **Отправка запроса:** Бэкенд отправляет HTTP-запрос в Search Service и прикрепляет токен в заголовок `Authorization: Bearer <токен>`.
3. **Search Service проверяет токен через зависимость (Depends):** Механизм внедрения зависимостей FastAPI перехватывает управление при вызове эндпоинта и по очереди проверяет:
   * Извлекает токен из заголовка с помощью `HTTPBearer`. Есть ли вообще токен в заголовке? (Если нет - автоматическая ошибка 401).
   * Цела ли подпись и правильный ли публичный ключ? (Если токен подделан - ошибка 401).
   * Не истекли ли 10 минут? (Если просрочен - ошибка 401).
   * Есть ли у Бэкенда права (`scopes` в payload токена) на это конкретное действие? (Если прав нет - ошибка 403).
4. **Выполнение:** Если все проверки пройдены, Search Service передает управление в функцию эндпоинта, выполняет запрос и возвращает успешный ответ 200 OK.

### План реализации

##### 1. Выпускаем токены на стороне Backend
#### Генерация ключей
* Сделать ключи для асимметричного шифрования.
* Добавить переменные для хранения ключей (публичный и приватный).
#### Создание модуля auth на Backend и логика кэширования
* Реализовать функцию создания JWT-токена с временем жизни 10 минут, который должен содержать информацию о сервисе и о его правах (`scopes`). Подписать приватным ключом.
* Реализовать логику in-Memory кэширования в памяти Backend.
* Добавить проверку: если токена нет или до истечения токена осталось <1 минуты - создать новый и обновить кэш; иначе берем из кэша.
#### Интеграция токена в HTTP-клиент Backend
* Найти место, где Backend вызывает Search Service.
* Добавить автоматическую подстановку заголовка `Authorization: Bearer <токен>` во все запросы к SS.

##### 2. Разработка на стороне Search service (Проверка токенов через FastAPI Dependencies)
#### Создание зависимости для проверки JWT в Search Service
* Создать модуль авторизации на стороне Search Service.
* Написать класс-зависимость, наследуемый от `fastapi.security.HTTPBearer`, для валидации токена публичным ключом.
* Реализовать внутри зависимости шаги проверки: наличие заголовка, валидность подписи, срок действия; в случае ошибок вызывать `HTTPException(status_code=401)`.
#### Разделение прав доступа
* Реализовать параметризуемую зависимость, принимающую список требуемых прав.
* Добавить в проверку токена валидацию права на конкретное действие.
* Если у сервиса (Backend) нет нужного уровня доступа в payload токена - возвращать `HTTPException(status_code=403, detail="Forbidden")`. Покрыть зависимостью нужные роуты Search Service.

##### 3. Проверка работы
#### Нагрузочное тестирование
* Провести базовое нагрузочное тестирование на эндпоинты Search Service с включенной проверкой токенов через зависимости.
* Посмотреть на поведение сервера и убедиться, что его процессор не зависает от постоянной проверки цифровых подписей внутри зависимостей на каждом входящем запросе.
